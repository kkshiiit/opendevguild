# User support, community feedback and learning from incidents

Use for a bounded support/feedback decision. Preparing a draft does not authorize
contacting users, posting publicly or changing account state.

## Inputs and procedure

1. Identify the user task, supported product/version, expected/observed behavior,
   impact, communication authority and privacy policy. Request only the minimal
   sanitized reproduction; never ask for tokens, production databases or unrelated
   personal information. Separate a report from a confirmed defect.
2. Classify troubleshooting, usability, feature request, billing, abuse, security
   incident or accessibility barrier. Route urgent safety/security material to the
   established restricted channel. Do not put embargoed details in public issues.
3. Reproduce with authorized synthetic fixtures and existing runbooks. Record
   environment, exact error, attempted steps and outcome. Avoid repeating actions
   that already failed unless changed evidence justifies a bounded retry.
4. Give clear recovery steps, known limits and next owner without unsupported
   promises or blame. Escalate missing authority, legal/billing decisions and
   irreversible remedies. Draft responses in the user's language where possible;
   do not claim a message was sent unless an authorized channel confirms it.
5. Consolidate duplicates and community themes using evidence counts and sampling
   limits. Keep vocal participants distinct from the entire user population;
   preserve dissent, accessibility needs and unresolved contradictory reports.
6. Convert validated fixes into a regression, documentation/runbook update and
   traceable issue disposition. Obtain separate review before changing reusable
   skill rules; a preference or support anecdote is a proposal, not training data
   or demonstrated product improvement.

## Output and gate

Return sanitized case summary, severity, reproduction evidence, action/draft,
owner, status, safe next step and retention decision. Accept closure only with
observed resolution or the explicit documented disposition. Reject invented user
feedback, secret collection, automatic contribution acceptance and unsupported
support/SLA guarantees.

Positive: turn a reproducible installation collision into a safe workaround and
regression report. Negative: an internal API refactor with no user report requires
no outreach. Pressure: reject posting a private transcript or refunding/deleting an
account without the appropriate authorization.
